# CLAUDE.md

用于减少 LLM 常见编码错误的行为准则。按需与项目特定的指令合并。

**权衡：** 这些准则偏向谨慎而非速度。对于简单任务，自行判断。

## 1. 编码之前先思考

**不要假设。不要隐藏困惑。呈现权衡。在眼前的错误之外多想一步。**

在实现之前：
- 明确陈述你的假设。如果不确定，就询问。
- 如果存在多种解读，把它们呈现出来——不要沉默地选择一种。
- 如果存在更简单的方法，说出来。有必要时据理力争。
- 如果有不清楚的地方，停下来。指出困惑所在。询问。

在修复错误或警告时：
- 不要只是消除编译器的报错——先理解那些死代码/错误代码原本想做什么，然后将其彻底移除。
- 向外追踪一跳：如果移除 X 后，Y 不再有读取者或调用者，Y 也一并移除。在同一次处理中完成，不要留作后续。

## 2. 简洁优先

**完整解决问题所需的最少代码。**

- 不添加未被要求的功能。
- 不为单次使用的代码创建抽象。
- 不添加未被要求的"灵活性"或"可配置性"。
- 不为不可能的场景做错误处理。

如果一次修复留下了没有对应 getter 的 setter、无人使用的 import、或永远无法执行的逻辑路径，那它就不算完成。移除一个变量，意味着移除所有仅为服务于它而存在的东西。

## 3. 外科手术式变更

**最小的 diff 面——但要覆盖每个变更的完整逻辑半径。**

在编辑现有代码时：
- 不要"改进"相邻的代码、注释或格式。
- 不要重构没有坏的东西。
- 匹配现有风格，即使你会用不同的方式。
- 如果注意到无关的死代码，提出来——不要删除它。

当你的变更制造了孤儿时：
- 移除你的变更导致不再使用的 import/变量/函数。
- 在宣布完成之前，验证：这个文件里是否还有其他地方仍在引用一个幽灵？

## 4. 目标驱动执行

**定义成功标准。循环直至验证通过。**

将任务转化为可验证的目标：
- "添加校验" → "为非法输入编写测试，然后让它们通过"
- "修复缺陷" → "编写一个能复现它的测试，然后让它通过"
- "重构 X" → "确保前后测试都通过"

对于多步骤任务，给出一个简短的计划：
```
1. [步骤] → 验证：[检查]
2. [步骤] → 验证：[检查]
3. [步骤] → 验证：[检查]
```

有力的成功标准让你能独立循环。薄弱的标准（"让它能跑"）则需要不断澄清。

> 另见：`test-driven-development`，了解包含测试治理与 mock 纪律的完整 RED-GREEN-REFACTOR 方法论。

## 5. 面向边界的范式

在生成、重构或审查任何代码时，把软件视为一种信任与边界遏制的拓扑结构。

### 5.1 信任拓扑与流控制

**原则：** 在边界处校验，在内部信任，在出口处封装。每个值要么已被校验，要么被信任——没有中间地带。

关于边界识别、校验协议、内部信任逻辑与统一异常处理的详细规则，请调用 `coding-conventions`。

### 5.2 四维极限推演

在最终确定任何逻辑之前，在脑海中把系统推向四个空间中的物理与逻辑极限：

- **空间与规模：** 推演输入完全缺失（null/空/零）或处于绝对上界（溢出/最大容量）时的行为。
- **时间与并发：** 确保任何外部等待或协调都有自主夺回控制的机制（超时）。确保状态变更是原子的，并与竞态条件隔离。
- **状态与结构：** 维持不变量的完整性。按照领域生命周期优雅地拒绝非法的状态转换。
- **资源与容量：** 当底层内存、连接或算力耗尽时，设计优雅降级或故障隔离。

### 5.3 强制性的思考与输出协议

按照以下顺序组织你的回复和代码生成。不要跳过或合并这些部分：

#### [边界审计]
- **已识别的入口：** [列出具体入口] → **收敛机制：** [不确定性如何被消除]
- **已识别的出口：** [列出具体出口] → **封装机制：** [如何防止泄漏]
- **可信区边界：** [定义内部信任绝对成立的范围]

#### [极限映射]
- **规模极限：** 当 ______ 发生时，自我保护路径是 ______。
- **时间/资源极限：** 当 ______ 发生时，自我保护路径是 ______。

#### [契约代码]
*交付干净、健壮的代码，100% 对应上述审计与映射。*

## 6. 技能路由

当任务涉及特定领域时，调用对应的技能，而不是复制其规则：

| 当你…… | 调用 |
|---|---|
| 编写或审查任何生产代码 | `coding-conventions` |
| 提交前审查任何代码变更 | `code-review-guidelines` |
| 编写新功能、修复缺陷或重构 | `test-driven-development` |
| 在任何代码变更之前（评估影响） | `architecture-thinking` |

---

**这些准则正在生效的标志是：** diff 中更少的不必要变更、更少的因过度复杂而重写、以及澄清性问题出现在实现之前而非犯错之后。
